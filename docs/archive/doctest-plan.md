# Doctest Plan

This document describes a plan to add doctest support to Turmeric's stdlib.
The goal is to make `;;;` Example blocks executable so that stdlib functions are
tested by the documentation that already exists, without requiring separate
`expected.stdout` fixture files that drift and need manual regeneration.

---

## 1. Motivation

Fixture tests in `tests/fixtures/` have two pain points:

1. Every new behavior requires creating a directory with at least two files
   (`input.tur`, `expected.stdout`). When output changes, both files must be
   updated in sync.
2. `expected.c` codegen snapshots compound this: any internal codegen change
   touches dozens of files even when behavior is unchanged.

The docstrings already contain the information needed for many tests:

```turmeric
;;; head -- extract the first element of a list.
;;;
;;; Example:
;;;   (head (cons 42 (nil-value)))  ; => 42
```

That `; => 42` annotation is the expected `println` output. A doctest runner
can extract these and verify them without any separate fixture file.

---

## 2. Scope

Doctests cover **stdlib `;;;` Example blocks only**. Fixture tests remain the
right tool for:

- Programs that require `run.args` or `input.stdin`
- Error/diagnostic fixtures (`expected.diag`)
- Codegen snapshots (`expected.c`)
- Multi-file programs or anything that crosses module boundaries non-trivially
- Async, networking, or timing-dependent behavior

Doctests and fixtures coexist; doctests do not replace the fixture runner.

---

## 3. The `; =>` annotation

### 3.1 Testable vs descriptive

Not every `; =>` line is mechanically testable. Examples fall into three
categories:

| Category | Pattern | Action |
|----------|---------|--------|
| **Scalar** | `(expr)  ; => 42` / `; => true` / `; => "hello"` | Run `(println expr)`, compare to `42` |
| **Display** | `(expr)  ; => list [1, 2]` | Skip (prose description, not a Turmeric literal) |
| **Descriptive** | `(expr)  ; => a function arrow that doubles its input` | Skip (semantics note, not a value) |

A `; =>` value is **testable** when it matches one of:

- An integer literal: `-?[0-9]+`
- A float literal: `-?[0-9]+\.[0-9]+`
- `true` or `false`
- A double-quoted string: `"[^"]*"`
- `nil` or `0` (nil-value result)

Everything else is treated as a prose description and skipped silently.

### 3.2 Multi-expression examples

Some `Example:` blocks evaluate a sequence of expressions to set up state
before the testable line:

```turmeric
;;; Example:
;;;   (def xs (cons 1 (cons 2 (nil-value))))
;;;   (head xs)  ; => 1
```

Lines in the block that lack `; =>` are emitted as setup statements.
Only the line(s) with `; => <testable-value>` generate a `println` + assertion.

---

## 4. Implementation

### Phase D0 -- Docstring extraction (extend `gendocs.py`)

`gendocs.py` already parses `;;;` blocks and stores `sections['example']` as a
raw string. Add a helper `extract_doctest_cases(doc)` that:

1. Splits the example string on newlines.
2. For each line:
   - If it has `; =>`, split on `; =>` to get `(expr, expected_raw)`.
   - If `expected_raw` matches the testable pattern (§3.1), emit a
     `DocTestCase(module, defn_name, setup_lines, expr, expected)`.
   - Otherwise, emit a `DocTestSetup(line)`.
3. Returns a list of `DocTestCase` objects.

No new parser: reuse the existing `parse_docstring()` path.

### Phase D1 -- Test file generator (`tools/doctest.py`)

A new standalone script (can import helpers from `gendocs.py`) that:

1. Accepts one or more stdlib `.tur` files (or a directory).
2. For each file, collects all `DocTestCase` objects.
3. Emits a single generated `.tur` test file per source module, e.g.
   `tests/doctest-generated/list.tur`, with the following structure:

```turmeric
; AUTO-GENERATED by tools/doctest.py -- do not edit.
(import "stdlib/list.tur")

(unsafe
  ; head: (head (cons 42 (nil-value)))  ; => 42
  (println (head (cons 42 (nil-value))))

  ; list-nil?: (list-nil? (nil-value))  ; => true
  (println (list-nil? (nil-value))))
```

All expressions are wrapped in a single `(unsafe ...)` block. `#{Unsafe}` is
an effect annotation that guards call sites, not a memory-safety suppressor;
wrapping the test harness in `(unsafe ...)` is the correct fix rather than
trying to infer per-expression unsafe requirements from the docstring alone.

Each generated file is a valid standalone Turmeric program. Running it with
`tur run` produces one line of output per testable example. The runner (D2)
compares those lines to the expected values.

Generated files go in `tests/doctest-generated/` (`.gitignore`d) and are
recreated on every `just doctest` run.

### Phase D2 -- Runner (`just doctest`)

Add a `tools/run-doctests.sh` (or extend `run.sh`) that:

1. Invokes `python3 tools/doctest.py stdlib/ --out tests/doctest-generated/`.
2. For each generated `.tur` file:
   a. Runs `tur run <file>` and captures stdout.
   b. Compares line N of stdout to the expected value for case N.
   c. On mismatch: prints `FAIL list:head -- got "41", expected "42"`.
3. Summarises pass/fail count; exits nonzero on any failure.

The runner reuses the stamp-cache pattern from `run.sh` (keyed on the source
`.tur` file mtime + tur binary mtime) so unchanged modules are skipped.

### Phase D3 -- `just` integration

```just
# Run stdlib doctests
doctest:
    python3 tools/doctest.py stdlib/ --out tests/doctest-generated/
    bash tests/run-doctests.sh

# Extend existing test target
test: build doctest
    bash tests/run.sh
```

`doctest` runs before the fixture suite so failures surface quickly without
waiting for the full compiled-fixture run.

### Phase D4 -- Stdlib audit

Walk every stdlib `;;;` Example block and verify:

1. Testable `; =>` lines produce correct output (fix any stale examples).
2. Non-testable lines are either intentionally descriptive or can be tightened
   to a scalar value.
3. Functions with no `Example:` block are noted for follow-up documentation.

This phase is a one-time cleanup; ongoing, new stdlib functions are expected to
have at least one testable example as part of the docstring standard.

---

## 5. Limitations and non-goals

| Limitation | Notes |
|------------|-------|
| Unsafe functions | All generated expressions are wrapped in a single blanket `(unsafe ...)` block. `#{Unsafe}` is an effect annotation, not a memory-safety suppressor, so this is safe in a test harness context. |
| Import cycles | Generated files do a single `(import "stdlib/X.tur")`; functions that depend on other stdlib modules rely on those modules' own imports. |
| Side-effecting examples | `println`, file I/O, or socket calls in an `Example:` block are skipped (no `; =>` scalar). |
| `expected.c` codegen | Doctests do not test codegen; that remains a fixture concern. |
| Error examples | `; => error: ...` is not supported in this plan; use an error fixture. |

## 6. File layout after implementation

```
stdlib/
  list.tur               -- source with ;;; Example blocks
  ...

tools/
  gendocs.py             -- extended with extract_doctest_cases()
  doctest.py             -- new: generates + optionally runs doctests
  run-doctests.sh        -- new: runner called by just doctest

tests/
  run.sh                 -- unchanged
  doctest-generated/     -- .gitignored generated test files
    list.tur
    option.tur
    result.tur
    ...

.gitignore               -- add tests/doctest-generated/
justfile                 -- add doctest target; extend test target
```

---

## 7. Resolved questions

1. **Multi-value examples**: single-line `; =>` only for now. Examples that
   produce multi-line output stay as prose descriptions. Revisit if multi-line
   patterns become common as more docstrings are written.

2. **`--emit-tur` integration**: `gendocs.py --emit-tur` should embed
   testability metadata in `stdlib/docstrings.tur` so the REPL `:doc` command
   can indicate which functions have verified examples. This is Phase D5 below.

---

## 8. Phase D5 -- `--emit-tur` testability metadata

After D1 runs and the set of verified functions is known, pass that information
to `gendocs.py --emit-tur` so `stdlib/docstrings.tur` records which functions
have at least one passing doctest.

### Runtime lookup table change

`docstrings.tur` today maps symbol names to doc strings. Extend each entry with
a `:verified` field (bool):

```turmeric
; Before
(doc-register "head" "head -- extract the first element...")

; After
(doc-register "head" "head -- extract the first element..." true)
(doc-register "list-print" "list-print -- print all elements..." false)
```

The third argument defaults to `false` for any function not covered by doctests.

### REPL display

`:doc head` appends a `[examples verified]` tag to the output when the field is
`true`. No change for unverified functions.

### Integration with the build

`tools/doctest.py` writes a machine-readable manifest of verified function names
to `tests/doctest-generated/verified.txt` after a successful run. `gendocs.py`
reads this file when `--emit-tur` is passed and sets the `:verified` flag
accordingly. If the file is absent (e.g. doctests have not been run yet), all
functions default to `false`.

The `just docs` target already calls `gendocs.py --emit-tur`; no change needed
there — the manifest is produced by `just doctest` beforehand, so the typical
workflow is:

```sh
just doctest   # runs tests, writes verified.txt
just docs      # regenerates docstrings.tur with verified flags
```

`just test` already calls `just doctest`, so CI gets both automatically.
