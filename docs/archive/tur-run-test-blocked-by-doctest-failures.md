# `tur run test` never reaches ctest -- the doctest dependency fails first

**RESOLVED 2026-08-20.** `tur run test` now runs to completion: doctests
159 passed / 0 failed, then ctest **108 passed / 0 failed** in 640s.

**Severity: medium** (the project's own top-level test recipe does not run the
test suite). Found 2026-08-20 while restoring `-j` to the same recipe
(`justfile-test-recipe-lost-ctest-j`).

## Repro

```sh
tur run test          # or: just test
echo $?               # 1, in ~24s -- far too fast for the suite
```

The recipe is `test: build doctest` followed by the ctest line. `doctest` runs
`tools/run-doctests.sh`, which exits 1 when any case fails
(tools/run-doctests.sh:155-160). That non-zero exit stops the chain, so **the
ctest line never executes**. The 24s wall clock is the giveaway: a real run is
minutes.

This is orthogonal to the `-j` regression next door -- restoring `-j` (done)
makes the ctest line correct, but the line is still unreachable.

## Current failures -- 50 cases across 4 modules

| Module | Cases | Shape |
|---|---|---|
| `rational` | 34 | cascade from one lint |
| `term` | 10 | `got "-1", expected "0"` |
| `panic` | 5 | cascade from one compiler warning |
| `seq-core` | 1 | `got "false", expected "true"` |

Two distinct causes:

**1. Diagnostic output desynchronises the expected/actual pairing.** The
`rational` and `panic` blocks are not 34 and 5 independent failures. The
compile emits a diagnostic on stderr -- for `rational` the
`unsafe block has 29 expressions (threshold: 20)` lint, for `panic` a
`-Wreturn-type` warning -- those lines land in the captured output, and every
subsequent case is then compared against the wrong line. The tell is failures
like ``got "1 | ; AUTO-GENERATED by tools/doctest.py -- do not edit.",
expected "2"``: the runner is reading the diagnostic's source echo as program
output. Silence or filter the diagnostics and both blocks likely collapse to
one real failure each, or zero.

**2. Genuinely wrong expectations.** `term/set-mode`, `term/set-raw`,
`term/set-cooked` etc. return `-1` where the docstring claims `0` -- these are
tty ioctls with no tty attached under the runner. `seq-core:empty-seq` returns
`false` for `true`. These are real docstring/environment mismatches.

Note `random:rand-bool` also fails intermittently (`got "0", expected "1"`) --
the docstring pins a coin flip, so the total oscillates between 50 and 51.

## Fix direction

1. Make the runner robust to diagnostics on the compile step -- capture
   stdout only, or filter `warning:`/`note:` lines before pairing. That alone
   should clear ~39 of the 50.
2. Fix or environment-gate the `term/*` tty cases (skip when
   `!isatty(STDIN_FILENO)`), `seq-core:empty-seq`, and the `random:rand-bool`
   coin flip.
3. Decide whether `test` should hard-depend on `doctest`. Given that doctests
   check *documentation examples*, gating the entire ctest suite behind them
   is a strong coupling; a separate `just doctest` plus a non-blocking report
   in `test` may fit better. Whichever way, `tur run test` must reach ctest.

## Resolution

### 1. The cascade was one bug, not 50 (51 -> 11)

`tools/run-doctests.sh` captured the generated program with `2>&1`. The
expected/actual pairing is **positional** -- the Nth line of stdout against
the Nth line of `<module>.expected` -- so every diagnostic line on stderr
shifted all later cases by one. The `rational` module's
`unsafe block has 29 expressions` lint desynchronised all 34 of its cases;
a gcc `-Wreturn-type` warning did the same to `panic`'s 5.

The report's own tell was right, and the shift is visible in the arithmetic:
`rational:rat/of!` reported ``got "7", expected "3"`` -- and `7` is the answer
to the *first* case, `(int/abs -7)`. The runner was reading each case's output
against its neighbour's expectation.

Fixed by capturing stdout and stderr separately. Program output is stdout;
diagnostics are stderr. The stderr text is not discarded -- the non-zero-exit
SKIP path now prints its first line, so an interpreter gap says which gap it
is instead of every module reporting an identical bare `exit 1`.

**51 failures -> 11.** The report predicted "~39 of the 50"; the actual was 40.

### 2. The remaining 11 were three different things

| Cases | Verdict |
|---|---|
| `term/*` (10) | Correct docs, unreproducible here |
| `seq-core:empty-seq` (1) | **Wrong docstring** |
| `random:rand-bool` | Non-deterministic; was flaking ~50% |

**`term/*`** -- the colour helpers return a plain copy when
`!isatty(1) || getenv("NO_COLOR")`, which their own `Returns:` sections
already document; `term/set-mode` and friends return `-1` with no tty on the
fd. The harness captures stdout through a pipe, so the examples are right as
documentation and simply cannot be checked here. They now carry an explicit
opt-out rather than being edited to enshrine the degraded output.

**`seq-core:empty-seq`** -- a genuinely wrong example, not an environment
problem. `seq-gen-done` tests `__state == -1`, i.e. "ran to completion", so a
freshly-created iterator is not done yet and `false` was the correct answer.
Verified the state machine is general before touching the docstring -- an
unstarted generator is `false` for a non-empty Seq too, and `true` after being
driven to completion in both cases:

```
(let [s (empty-seq)] (seq-gen-done (seq-iter s)))                  ; => false
(let [g (seq-iter (empty-seq))] ... (seq-gen-next g) ... done)     ; => true
(let [s (seq-of 7)] (seq-gen-done (seq-iter s)))                   ; => false
(let [g (seq-iter (seq-of 7))] ... two nexts ... done)             ; => true
```

The example now drives the iterator once and says why.

**`random:*`** -- seeded from `time(NULL)`, so genuinely non-deterministic.
The interesting part is why only `rand-bool` failed: `rand-int`, `rand-float`
and `rand-die` all pin a value too, but their trailing prose
(`; => 4  (simulate a die roll)`) stops the anchored `TESTABLE_RE` matching,
so they were being dropped **silently and by accident**. `rand-bool`'s bare
`; => 1` was testable, hence a coin flip run as an assertion. All four are now
explicitly annotated, so the three that were accidentally safe stay safe if
someone tidies the prose.

### 3. The opt-out is declared, not accidental

A trailing `; doctest: <reason>` on the `; =>` line:

```turmeric
;;;   (term/bold "hello")  ; => "\x1b[1mhello\x1b[0m"  ; doctest: stdout must be a tty (plain copy otherwise)
```

`tools/doctest.py` **reports** these rather than dropping them quietly, so a
module that stops being covered says so instead of just getting smaller.

Coverage was checked against `origin/main` rather than assumed: 415 cases on
main, 425 on the branch. Per-module, +6 `arc`, +2 `cstr`, +1 `mutex`,
+2 `option`, +2 `rwlock`, +7 `stm-sync` from this branch's new stdlib, and
`term` 12 -> 2 from the opt-outs. Net +10, no module lost coverage.

### 4. On the `test: build doctest` coupling (report item 3)

Kept. Doctests are cheap and they do catch real doc rot -- this exercise
found a wrong `empty-seq` example and a flaking assertion. What made the
coupling expensive was not the dependency but its *silence*: the recipe
exited 1 in ~24s, which reads like a fast test run rather than no test run.

So the failure path now says what it costs -- that the chain stops here, that
`tur run test` did not reach ctest, and how to invoke ctest directly
meanwhile. Section 5 of the portability guide gains the same warning, plus
the stdout/stderr rule and the annotation convention.
