# Source Layout Plan

A plan for reorganising the C/H files across the project. Three questions
addressed in order: root-level flotsam, flat `src/` structure, and the two
outsize translation units.

---

## 1. Root-level `.c` / `.h` files

`adder.c`, `adder.h`, `myapp.c`, `myapp.h`, `input.c`, `input.h`, `str.c`,
`str.h`, `time.c`, `time.h` are **compiler output** — each starts with
`/* generated by tur (phase 2) */`. They are stale artefacts from manual
test runs and have no place in version control.

**Action:** delete them and add a `.gitignore` pattern so they never reappear.

```gitignore
# Generated C/H output from `tur build` / `tur emit-c`
*.c
*.h
!src/**/*.c
!src/**/*.h
!tests/**/*.c
!tests/**/*.h
```

The negative patterns ensure genuine sources under `src/` and `tests/` are
still tracked. Alternatively, redirect all `tur build` output to a dedicated
`out/` directory and add `out/` to `.gitignore`.

---

## 2. Directory structure for `src/`

`src/` currently holds ~65 files at a single level. Five natural subsystems
are already visible from naming alone; grouping them makes it obvious where
to look for any given piece of functionality, and keeps `src/CMakeLists.txt`
structured rather than a single flat list.

### Proposed layout

```
src/
├── main.c                  # CLI entry point only
│
├── compiler/               # frontend pipeline: text → IR
│   ├── reader.{c,h}        # lexer / S-expression parser

│   ├── types.{c,h}         # type system representation

│   ├── builtins.{c,h}      # built-in primitive table
│   ├── typeclass.{c,h}     # typeclass environment
│   ├── diag.{c,h}          # diagnostics (errors, warnings, codes)
│   ├── fmt.{c,h}           # source pretty-printer
│   ├── pkg.{c,h}           # Spice package manager (Phase PKG-1)
│   ├── elab.{c,h}          # elaborator (see §3 for further split)
│   └── emit.{c,h}          # C codegen  (see §3 for further split)
│
├── passes/                 # analysis and transformation passes
│   ├── borrow_check.{c,h}  # ownership / move / borrow analysis
│   ├── kind_check.{c,h}    # HKT kind inference
│   ├── cps.{c,h}           # CPS transform for shift/reset
│   ├── effect.{c,h}        # effect type representation
│   ├── effect_check.{c,h}  # effect-row inference
│   ├── effect_lower.{c,h}  # algebraic effects → shift/reset
│   ├── lifetimes.{c,h}     # lifetime annotation IR
```

### Notes on naming collisions

`src/async/fiber.{c,h}` and `src/turi/fiber.{c,h}` have the same basename
but are entirely different modules (stackful async fiber vs. REPL coroutine).
CMake references them by path (`async/fiber.c` vs. `turi/fiber.c`), so there
is no linker collision. If the duplication is confusing, `async/fiber.c` can
be renamed `async/stack_fiber.c` to make the distinction explicit.

### CMakeLists changes

Each new subdirectory gets an `add_subdirectory()` call (or its sources are
listed with path prefixes). The simplest migration is to keep a single
`src/CMakeLists.txt` and update the source lists with the new prefixes —
no new `CMakeLists.txt` files per subdirectory needed unless the project
grows further.

```cmake
# before
set(TUR_CORE_SOURCES reader.c forms.c elab.c ...)

# after
set(TUR_CORE_SOURCES
    compiler/reader.c  compiler/forms.c  compiler/elab.c  ...
    passes/borrow_check.c  passes/kind_check.c  ...
    runtime/arena.c  runtime/rc.c  ...
    async/fiber.c  async/scheduler.c  ...
    ${TURI_EVAL_SOURCES}
)
```

All internal `#include` directives that use bare filenames
(`#include "reader.h"`) continue to work unchanged because
`target_include_directories(tur_core PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})`
already puts `src/` on every compiler's include path. Files in subdirectories
that include headers from sibling subdirectories will need the relative prefix
(`#include "compiler/diag.h"` instead of `#include "diag.h"`), but that
change is mechanical and grep-friendly.

## 3. Splitting the large translation units

Two files dominate the build: `elab.c` (17,889 lines, 784 KB) and `emit.c`
(8,347 lines, 408 KB). Both have grown substantially since this plan was first
written (elab.c was 11,850 lines, emit.c was 6,948 lines), driven by the
addition of algebraic effects, contract types, union/intersection types, and
the Spice package manager. Both retain clear internal section boundaries
already marked by `/* Phase N: ... */` comments.

### 3a. `emit.c` — recommended first (medium effort, low risk)

`emit.c` has well-separated concerns and almost no internal forward
declarations. The natural split is:

| New file | Approx lines | Contents |
|---|---|---|
| `emit_core.c` | ~650 | `EmitCtx`, naming helpers (`name_for_binding`, `mangle_field_name`), atom constructors, `emit_c_string`, `emit_builtin`, deferred-thunk machinery |
| `emit_expr.c` | ~1,900 | `emit_value`, `emit_let_value`, `emit_if_value`, `emit_do_value` — expression-position emission |
| `emit_stmt.c` | ~700 | `emit_stmt`, `emit_while_stmt`, `emit_set_stmt` — statement emission |
| `emit_fns.c` | ~2,700 | `emit_fn_def`, closure environments, typeclass dict emission, RC/cloneable-cont emission |
| `emit_effects.c` | ~1,200 | algebraic effects, CPS shift/reset, continuation frame emission |
| `emit_module.c` | ~1,200 | `emit_header_file`, `emit_impl_file` — module codegen |

> **Note:** These estimates are scaled from the original plan proportionally;
> actual boundaries should be verified against `emit.c` section markers before
> splitting.

An `emit_internal.h` header (not installed, included only by `emit_*.c`)
would expose `EmitCtx` and the static helper declarations that need to be
visible across translation units. The public `emit.h` stays unchanged.

### 3b. `elab.c` — highest impact, highest effort

`elab.c` is the largest file in the project and encompasses the entire type
elaborator: ~20 distinct "phases" are all woven together through the shared
`Elab` struct, forward declarations, and scope-walking helpers. Splitting it
carelessly risks creating circular include chains or shadow-declaring the same
struct in two translation units.

The safest strategy is an **internal header + file-per-phase** approach:

```
compiler/
    elab.h              # public API: elaborate_program() only
    elab_internal.h     # Elab struct, Scope, MacroDef, forward decls of all
                        # static helpers — included only by elab_*.c files
    elab_core.c         # Elab struct init, scope helpers, free-var analysis,
                        # intern_cstr, binding helpers
    elab_macros.c       # defmacro, quasiquote, gensym, macro expansion
    elab_fns.c          # defn, fn, extern-c, closure elaboration
    elab_structs.c      # defstruct, make-struct, borrow traits
    elab_typeclasses.c  # defclass, definstance, kind aliases, HKT,
                        # method-call dispatch
    elab_memory.c       # rc/weak/ref/gc primitives, Phase 9 & 10
    elab_effects.c      # defeffect, perform, handle, shift/reset,
                        # cloneable continuations, Phase 18/19/B2
    elab_contracts.c    # contract types (require!/ensure!/assert!),
                        # Phase CT
    elab_unsafe.c       # ptr-deref/write/add, unsafe-cast, reinterpret,
                        # raw-malloc/free, Phase U3
    elab_module.c       # module load, import, export, Phase M
    elab_call.c         # function-call elaboration, method dispatch,
                        # threading macros (-> and ->>)
    elab_toplevel.c     # elaborate_program entry point, top-level form
                        # dispatch
```

Target: no single file above ~2,000 lines.

> **Note:** The original per-file line estimates from this plan are stale —
> elab.c has grown from ~11,850 to ~17,889 lines. Re-baseline the estimates
> by grepping for `/* Phase` section markers before starting the split. A new
> `elab_contracts.c` is needed to house contract-type elaboration, which did
> not exist when this plan was written.

**The critical constraint** is that every `elab_*.c` file is a single
translation unit that still needs `static` linkage for internal helpers
(otherwise the linker sees duplicate symbols). The solution is to keep all
helpers `static` inside their own file and introduce a small number of
non-static functions — prefixed `elab_` — for cross-file calls. All such
cross-file calls must be declared in `elab_internal.h`.

**Order of attack:**
1. Extract `elab_macros.c` first — macro infrastructure is almost
   self-contained and has the fewest cross-dependencies.
2. Extract `elab_unsafe.c` — equally self-contained.
3. Extract `elab_effects.c` — well-delimited Phase 18/19/B2 block.
4. Extract `elab_module.c` — Phase M is already somewhat isolated.
5. Extract `elab_memory.c` — Phase 9/10 rc/gc cluster.
6. Tackle `elab_fns.c`, `elab_structs.c`, `elab_typeclasses.c` last,
   since they share more with the core Elab state.

Each extraction should be paired with a full test run (`just test`) before
moving to the next, since elab is on the critical path for every fixture.

## Priority summary

| Priority | Work | Effort | Benefit |
|---|---|---|---|
| 1 | Delete root generated files + add `.gitignore` | Trivial | Removes noise from every `git status` |
| 2 | Move files into `compiler/`, `passes/`, `runtime/`, `async/`, `web/` + update `CMakeLists.txt` | ~1 day | Navigation, grep locality, mental model |
| 3 | Split `emit.c` into 6 files via `emit_internal.h` | ~2–3 days | Faster incremental builds, clearer codegen stages; emit.c is now 8,347 lines |
| 4 | Split `elab.c` into ~12 files via `elab_internal.h` | ~2 weeks | Biggest win for readability and build times; highest risk; elab.c is now 17,889 lines |

Items 1–2 are independent of each other and of 3–4. Items 3 and 4 are also
independent. The directory reorganisation (item 2) should happen before the
file splits (items 3–4) so that the new files land in the right place from
the start.
