# Recombine `turmeric-spices` into the `turmeric` Repo

## Motivation

The split between `turmeric` (this repo) and `rjungemann/turmeric-spices`
(sibling repo at `../turmeric-spices`) has been a persistent source of
friction, most acutely in the web Claude Code sandbox where the harness
checks out exactly one repo. Web sessions launched against `turmeric`
have repeatedly:

- claimed they could "just clone the sibling" and ship spice PRs --
  then thrown the work away because there is no push target,
- silently scaffolded local `spices/` trees that violate
  `CLAUDE.md`'s "spices live in `../turmeric-spices`" rule,
- produced patches against a phantom working tree the user then has to
  reconstruct by hand.

The split also costs in everyday workflow: every spice fixture is
gated on `requires.spices`, every per-file CLI command has to walk up
into a sibling dir, the REPL auto-discovery has a sibling-only escape
hatch, and CI matrices have to special-case "spices present? yes/no".

Recombining the trees removes all of that. There is no plausible future
where the two repos are released or versioned independently -- the
compiler ABI and the spice manifests change in lockstep already.

## Target Layout

```
turmeric/
  src/                    -- compiler (unchanged)
  stdlib/                 -- core stdlib (unchanged)
  tests/                  -- compiler test fixtures (unchanged)
  spices/                 -- NEW: every spice lives here
    json/
      build.tur
      src/
      tests/
      vendor/             -- per-spice vendored C, see "Loose C files" below
    raylib/
    ...                   -- 37 spice dirs total
  docs/
```

Every spice becomes a workspace member of the top-level `build.tur`
(or stays self-contained with its own manifest; see "Workspace shape"
below).

## Inventory of What Moves

From `../turmeric-spices/`:

- `web/` -- the **`spices.turmeric-lang.com`** Cloudflare Worker
  (separate `wrangler.jsonc` with `name: turmeric-spices` and a custom
  `spices.turmeric-lang.com` route; serves rendered per-spice docs).
- `spices/` (37 dirs): `ansi`, `c-dsl`, `ecs`, `ecs-raylib`, `frame`,
  `glsl`, `http`, `httpd`, `json`, `linalg`, `math`, `notebook`,
  `opengl`, `osc`, `plot`, `plutovg`, `png`, `postgres`, `raygui`,
  `raylib`, `regex`, `rtaudio`, `rtmidi`, `scscm`, `sdf-raylib`,
  `signal`, `sqlite`, `stats`, `template`, `test`, `tidal`, `tls`,
  `tourist`, `valkey`, `watch`, `wav`, `zlib`.
- `build.tur` (root manifest with `:members` list of all spices).
- `Justfile`, `CLAUDE.md`, `README.md`, `.github/`, `tools/`, `vendor/`,
  `web/`, `scripts/`, `.gitignore`.
- Note: the ~203 loose `*__*.{c,h}` files visible at
  `../turmeric-spices/` root are `tur emit-c` artifacts (file header
  reads `/* generated by tur (phase 2) */`) and are **already
  gitignored** by the spices `.gitignore` (`/*__*.c`, `/*__*.h`,
  plus `/event.{c,h}`, `/*.manifest`, `/tur.lock`). They are
  untracked, so `git subtree add` will not import them. No source-side
  cleanup needed; the merge picks up *only* tracked files. The
  underlying leak -- running `tur emit-c`/`tur build` from the repo
  root with no `--build-dir` -- is unchanged by the merge and
  addressed in Phase 2 below by carrying the same `/*__*.{c,h}` /
  `/event.{c,h}` / `/*.manifest` / `/tur.lock` entries forward into
  the merged repo's root `.gitignore`.

## Plan

### Phase 0 -- Decisions to lock down before any code moves

1. **Workspace shape.** Two options:
   - (a) One top-level `build.tur` lists every spice as a `:member`.
     Pros: one `tur build` builds the world; matches today's
     `turmeric-spices/build.tur`. Cons: turmeric root manifest now has
     a 40-entry member list mixed with compiler concerns.
   - (b) Each `spices/<name>/build.tur` stays standalone; there is no
     top-level workspace. Pros: clean separation; spice authors keep
     working per-spice. Cons: no single "build all spices" command;
     CI has to enumerate.
   - **Recommendation: (a)** with the member list in a dedicated
     `spices/build.tur` workspace manifest (turmeric root stays
     compiler-only). The compiler's own `build.tur` stays untouched.

2. **Loose root-level C files: no action needed at source.** Already
   gitignored in the spices repo; not in history; not in the subtree
   merge. The merge import is clean by construction. The only
   carry-forward task is to make sure the merged turmeric `.gitignore`
   has the same root-anchored patterns
   (`/*__*.c`, `/*__*.h`, `/event.c`, `/event.h`, `/*.manifest`,
   `/tur.lock`) so the same `tur` invocations from the merged-repo
   root don't start producing tracked junk here either. Done in
   Phase 2.

3. **Git history preservation.** Choose between:
   - `git subtree add --prefix=spices/ ../turmeric-spices main` --
     preserves history, single merge commit, no rewriting.
   - `git filter-repo` to rewrite spice paths under `spices/<name>/`
     before merging -- cleaner final layout but expensive and
     irreversible on the spices repo.
   - **Recommendation: subtree** -- the messy root-level C files become
     a tracked subtree-merge artifact we then clean up in normal
     commits. History stays inspectable via `git log -- spices/json/`.

4. **What happens to the old repo.** Archive
   `rjungemann/turmeric-spices` (read-only, README points at this
   repo's `spices/` tree). Do not delete -- old issues, PRs, and
   external links still need to resolve.

### Phase 1 -- Merge

1. Run `git fetch` on the sibling, then
   `git subtree add --prefix=spices-staging ../turmeric-spices main`
   in this repo. The staging prefix lets us settle files into their
   final homes without colliding with existing turmeric paths.
2. Move `spices-staging/spices/*` -> `spices/*`.
3. (No loose-C step needed; see Inventory note and Phase 0.2.)
4. Resolve overlaps with existing turmeric files: `Justfile` (merge
   recipes), `CLAUDE.md` (merge spice-side rules into a
   `spices/CLAUDE.md` so they only apply when editing under
   `spices/`), `.gitignore`, `README.md`, `tools/`, `vendor/`, `web/`.
5. Delete `spices-staging/`.
6. Author `spices/build.tur` workspace manifest per Phase 0.1.

### Phase 2 -- Build & test wiring

1. **`tests/run.sh` / `tests/run-turi.sh`**: drop the
   `requires.spices` skip logic -- the checkout is always present now.
   Keep the marker file recognized for one release as a no-op so
   external forks don't break, then remove.
1a. **`.gitignore`**: append the spices-repo root-anchored patterns
   (`/*__*.c`, `/*__*.h`, `/event.c`, `/event.h`, `/*.manifest`,
   `/tur.lock`) so the existing `tur emit-c`/`tur build`-from-root
   leak doesn't start producing tracked junk in the merged repo.
2. **`CMakeLists.txt`**: the two existing references
   (lines 34, 179 -- both "spices may be absent" carve-outs) can be
   simplified to assume presence.
3. **Fixtures referencing `../turmeric-spices`** (10 files found):
   - `tests/run-tur-new.sh`
   - `tests/run-scscm-compile.sh`
   - `tests/run-transitive-cmake-deps.sh`
   - `tests/run-turi.sh`
   - `tests/run.sh`
   - `tests/fixtures/httpd-mw-compress/build.tur`
   - `tests/fixtures/scscm-compile/build.tur`
   - `tests/fixtures/scscm-compile/scscm-compile.tur`
   - `tests/fixtures/errors/ecs-defsystem-writes-unauthorized/build.tur`
   - `stdlib/httpd-compress.tur`

   Rewrite each `../turmeric-spices/spices/<name>` to
   `<repo-root>/spices/<name>`. Use the same anchor mechanism
   `tur fetch`/`tur build` already uses for `:path` deps relative to
   the manifest (`:path "../../../../spices/<name>"` from a fixture
   dir, or expose a project-root anchor like `${TUR_ROOT}` if the
   spice tree decision in Phase 0.1 makes that cleaner).
4. **Regenerate codegen snapshots** for any fixture whose path string
   appears in `expected.c` (grep before regenerating, per `CLAUDE.md`
   "Fixture Snapshots" rule). Same-PR regen, not a follow-up.
5. **Per-file CLI auto-discovery** (`tur check`, `tur emit-c`,
   `tur run <file>`) already walks up to `build.tur` -- behavior is
   unchanged. The `--no-auto-spice` flag and `TUR_NO_AUTO_SPICE`
   env var keep their meanings; nothing to change.
6. **REPL auto-discovery** (`tur repl` -> `.tur-repl-cache/`): no
   code changes; the cache dir lands in whichever spice you cd into.

### Phase 2.5 -- Preserve dual-site deploys

The two domains stay independent Cloudflare Workers, each with its own
`wrangler.jsonc`, custom-domain route, and deploy recipe. The merge
must not collapse them into one site.

| Domain | Source today | Source after merge | Wrangler `name` |
|---|---|---|---|
| `turmeric-lang.com` (+ `try.turmeric-lang.com`) | `turmeric/web/` | `turmeric/web/` (unchanged) | `turmeric` (existing) |
| `spices.turmeric-lang.com` | `turmeric-spices/web/` + `turmeric-spices/wrangler.jsonc` | `turmeric/spices-web/` (new dir) | `turmeric-spices` (unchanged) |

Concretely:

1. Move the sibling's `web/` tree to `spices-web/` at the turmeric
   root (not `spices/web/` -- keep it out of the workspace member
   list so `tur build spices/` doesn't try to compile a Cloudflare
   Worker bundle). Move `turmeric-spices/wrangler.jsonc` alongside it
   as `spices-web/wrangler.jsonc`. The Worker `name` stays
   `turmeric-spices` and the `spices.turmeric-lang.com` custom-domain
   route is preserved verbatim -- Cloudflare keeps serving the same
   Worker under the same hostname, no DNS/cert changes.
2. Port the sibling `Justfile`'s `web-dev` and `deploy-web` recipes
   into this repo's `Justfile` as `spices-web-dev` and
   `deploy-spices-web`, pointing at `spices-web/` and the new
   `tur run docs` output for spice modules. The existing turmeric
   `deploy-web` recipe (-> `turmeric-lang.com`) stays exactly as it
   is.
3. CI: today, deploy on push to `main` runs in the spices repo's
   `.github/workflows/`. Port that workflow into
   `turmeric/.github/workflows/deploy-spices-web.yml`, gated on a
   path filter so it only runs when `spices-web/**`, `spices/**`,
   or `docs/api/spices/**` changes. The existing
   `deploy-web.yml` (or equivalent) stays gated on `web/**` and
   `stdlib/**`/`docs/api/**`. Result: a stdlib-only PR triggers one
   deploy, a spice-only PR triggers the other, a touch to both
   triggers both -- but they never block each other.
4. Cloudflare account: both Workers already live in the same
   Cloudflare account today (same `wrangler login`). After the merge
   the merged-repo CI needs `CLOUDFLARE_API_TOKEN` secrets for *both*
   Workers -- audit which token the spices repo's Actions use and
   either reuse it or mint a new one scoped to both Workers before
   the first CI deploy.
5. Smoke test in Phase 4: hit both `https://turmeric-lang.com` and
   `https://spices.turmeric-lang.com` after the first post-merge
   deploy, and confirm the spices site still serves per-spice doc
   pages (not the turmeric homepage) -- a misrouted Worker would
   silently 200 with the wrong content.

The "spices doc site" pipeline -- `tur run docs` enumerating
`spices/<name>/` and emitting per-spice HTML into
`docs/api/spices/<name>/`, then `spices-web/` packaging that into the
Worker assets dir -- replaces the sibling repo's docs build step.
This is the only behavioral change to the spices site; the URL,
routing, and Worker identity all stay the same.

### Phase 3 -- Doc and rule cleanup

1. **`CLAUDE.md`** -- delete the entire "Spice Repository Layout" and
   "Web Claude ... do not pick up spice work" sections; replace with
   a one-paragraph "Spices live under `spices/`; each is its own
   workspace member of `spices/build.tur`." Drop the "do not create
   `./spices/`" rule -- it now exists.
2. **`docs/guides/developing-spices-guide.md`** -- rewrite paths,
   remove the "sibling checkout" preamble.
3. **`docs/guides/repl.md`** -- drop sibling-repo guidance.
4. **`README.md`** -- mention spices in the top-level layout section.
5. Update auto-memory entries that assume the sibling layout
   (`project_p2a_derive_json_minimal.md`,
   `project_sdf_raylib_phase.md`) to reference in-tree paths.

### Phase 4 -- Validation gate

Before opening the merge PR:

- `bash tests/run.sh 2>&1 | grep "^FAIL"` -- must be empty
  (~1442 fixtures, ~4-5 min).
- `bash tests/run-turi.sh 2>&1 | grep "^FAIL"` -- must be empty.
- `tur build spices/` (or whatever Phase 0.1 settles on) must build
  every spice from a clean tree on macOS and Linux.
- Smoke-test one spice per "exotic dep" category to confirm vendored
  C and `:url` deps resolve: `raylib` (GLFW/raylib), `sqlite`
  (vendored sqlite3), `postgres` (libpq), `rtaudio`/`rtmidi`
  (PortAudio/RtMidi), `plutovg`, `tls`.
- Run `tur run docs` -- generated `docs/api/` should now include
  spice modules.

### Phase 5 -- Archive sibling repo

1. Push a final commit to `rjungemann/turmeric-spices` updating its
   `README.md` to: "This repo has been merged into
   `rjungemann/turmeric` under `spices/`. New work happens there."
2. Archive the repo via the GitHub setting (read-only).
3. Leave open issues open -- they're still findable, and the new
   location is one click away via the archived README.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Subtree merge pulls in 203 loose root-level generated C files | Phase 1.0 deletes them at the source before subtree-add; also fix whatever build invocation in the spices repo is leaking them to the repo root, or they will reappear post-merge |
| Fixture path rewrites silently miss a `${...}/turmeric-spices` reference baked into a `.c` snapshot | Grep `tests/fixtures/**/expected.c` for the literal string `turmeric-spices` before and after; both must be empty after |
| External users with `:url`-pinned deps on `github.com/rjungemann/turmeric-spices` break when the repo archives | Archived GitHub repos still serve `git clone` over HTTPS, so existing `tur fetch` pins keep working; document this and stop publishing new tags from the archived repo |
| CI on the spices repo gets orphaned mid-merge | Disable spices-repo Actions in Phase 5.1 before archiving; turmeric CI takes over coverage in Phase 4 |
| Auto-memory entries still claim "edit in `../turmeric-spices`" after merge | Phase 3.5 -- rewrite, don't trust grep alone, walk every project memory referencing spices |

## Out of Scope

- Changing what spices *do* (no API changes, no consolidations).
- Renaming spices (e.g. `c-dsl` -> `cdsl`). If a rename is wanted, it
  is a separate PR after the merge lands.
- Migrating spice issues from the old repo's tracker -- leave them
  where they are; link from the archived README.
