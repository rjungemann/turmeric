# Plan: Per-Spice CI Workflows (Real Per-Spice Badges)

> **Status:** Draft
> **Last Updated:** 2026-06-07
> **Type:** CI / Tooling
> **Affects:** `turmeric-spices/.github/workflows/`, `turmeric-spices/tools/`,
> spice READMEs.

---

## Overview

`turmeric-spices/.github/workflows/ci.yml` is one workflow that fans out
a matrix over `os × spice` (~34 spices × 2 OSes today). GitHub's built-in
badge URL is **per-workflow, not per-matrix-leg**, so the only available
badge today is aggregate: it goes red whenever any spice on any OS fails.

This plan replaces the single matrix workflow with **one generated
workflow file per spice** so each spice has its own real CI badge URL
and its own status independent of every other spice.

---

## Motivation

- **Honest per-spice status.** A `frame` bug should not turn `tourist`'s
  README badge red. Today it does.
- **Faster targeted reruns.** Re-running CI for one spice is one
  workflow re-run, not a matrix-wide one.
- **Cleaner failure attribution in PRs.** PR checks list workflows by
  name; per-spice workflows show as `CI / tourist`, `CI / frame`, etc.,
  instead of a single `CI / test-spice (tourist, ubuntu-latest)` row
  that disappears into a long matrix.
- **Per-spice badges in spice READMEs.** Currently impossible without a
  custom shields.io endpoint; this is the simple fix.

Cost we are accepting: ~34 generated YAML files in the repo (one per
spice). Mitigations under "Generator" and "Sync check" below.

---

## Non-Goals

- **No change to test semantics.** The per-spice steps (parse
  `build.tur`, fetch `:cmake-deps`, `tur check` every `*.tur`,
  `tur test` flat-or-nested) must remain bit-identical to today's
  `test-spice` job body.
- **No change to the `manifest-parse` and `discover-spices` jobs'
  *intent*.** They stay, possibly under different names. `discover-spices`
  becomes redundant (the workflow files themselves enumerate spices) and
  is dropped; `manifest-parse` stays as a repo-wide sanity workflow.
- **No new dependencies in CI.** The generator is Python 3.12 (already
  used by the workflow today) -- no Node, no Bash-only.

---

## Current State (audit)

`turmeric-spices/.github/workflows/ci.yml` defines:

1. `discover-spices` -- shell+python; enumerates `spices/*/build.tur`
   into a JSON array, output `spices`.
2. `test-spice` (matrix `os × spice`, `needs: discover-spices`) -- the
   real per-spice work: checkout, install deps, build `tur`, fetch
   `:cmake-deps`, `tur check src/**`, `tur test` flat-or-nested.
3. `manifest-parse` -- parses every `build.tur` regardless of matrix.

The badge URL today is:

```
https://github.com/rjungemann/turmeric-spices/actions/workflows/ci.yml/badge.svg
```

Goes red on any failure in any of the three jobs above.

---

## Target State

For each spice `<name>` in `spices/`:

```
.github/workflows/spice-<name>.yml      (generated)
```

Each file is a standalone workflow named exactly `<name>` (so the
badge URL is `…/actions/workflows/spice-<name>.yml/badge.svg` and the
display name in the Actions UI is just the spice name). Its single job
runs the same steps as today's `test-spice` body, with the matrix
collapsed to `os` only (`spice` is fixed per file).

Plus two repo-level workflows that stay shared:

```
.github/workflows/manifest-parse.yml    (was the manifest-parse job)
.github/workflows/spice-ci-sync.yml     (new: see "Sync check")
```

`ci.yml` is **deleted** at the end of the migration. No aggregate badge
is preserved (we have an explicit decision-record below on why).

Per-spice badge URL:

```markdown
[![CI](https://github.com/rjungemann/turmeric-spices/actions/workflows/spice-tourist.yml/badge.svg)]
```

Per-spice READMEs each get exactly this badge, with `<name>` substituted.

## Design

### Workflow file shape

One template, parameterized only by spice name:

```yaml
# .github/workflows/spice-<name>.yml
# AUTO-GENERATED by tools/gen-spice-workflows.py.
# DO NOT EDIT BY HAND. Edit the template + regenerate.
name: <name>
on:
  push:
    branches: [main]
    paths:
      - 'spices/<name>/**'
      - 'tools/gen-spice-workflows.py'
      - '.github/workflows/spice-<name>.yml'
  pull_request:
    branches: [main]
    paths:
      - 'spices/<name>/**'
      - 'tools/gen-spice-workflows.py'
      - '.github/workflows/spice-<name>.yml'
  workflow_dispatch: {}

jobs:
  test:
    name: ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest]
    steps:
      # (identical step body to today's test-spice, with the spice path
      #  hardcoded to spices/<name>)
      ...
```

Two design choices baked in:

1. **`paths:` filter.** Editing one spice only runs that spice's
   workflow. With 34 workflows this is essential -- without `paths:`
   every PR runs every workflow regardless of what it touched. The
   filter also includes the generator and the workflow file itself so
   meta-changes still re-run the spice.
2. **`workflow_dispatch:` enabled.** Lets us hit "Run workflow" from
   the UI for a single spice when we need to (e.g., transient flake,
   external dep changed) without touching code.

### Generator

`turmeric-spices/tools/gen-spice-workflows.py`:

- Enumerates `spices/*/build.tur` (same discovery as today's
  `discover-spices` job).
- Renders the template above into
  `.github/workflows/spice-<name>.yml` for each spice.
- Removes any orphan `spice-<name>.yml` whose spice no longer exists.
- `--check` mode: re-render in-memory and diff against the on-disk
  files; non-zero exit if any drift. Used by the sync-check workflow.
- Single source of truth for the template (kept inline as a Python
  string literal, with a `# AUTO-GENERATED` banner emitted into each
  file).

Run locally:

```sh
python3 tools/gen-spice-workflows.py             # write
python3 tools/gen-spice-workflows.py --check     # verify in CI
```

### Sync check

`.github/workflows/spice-ci-sync.yml` (small, fast, repo-wide):

```yaml
name: spice-ci-sync
on:
  pull_request:
    paths:
      - 'spices/*/build.tur'
      - 'tools/gen-spice-workflows.py'
      - '.github/workflows/spice-*.yml'
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: '3.12'}
      - run: python3 tools/gen-spice-workflows.py --check
```

This is the guardrail that makes "34 generated files" maintainable:
adding a spice without regenerating, or hand-editing one of the
generated files, fails this check on the PR.

### `manifest-parse` workflow

Lifts the existing `manifest-parse` job out of `ci.yml` into its own
file (`.github/workflows/manifest-parse.yml`), unchanged. It is
repo-wide so it stays on every PR, no `paths:` filter.

### Badge wiring

Once the workflows exist, two doc edits:

- `turmeric-spices/README.md`: replace the aggregate badge sentence
  with a small Markdown table (one row per spice: name, badge,
  link to spice README), generated by the same generator as a
  `--write-readme-table` mode (keeps the table in sync with the
  workflow files).
- Per-spice `spices/<name>/README.md`: prepend the
  `[![CI](...)](...)` line. Same generator handles this with
  `--write-spice-readme-badges` (idempotent: if the badge line is
  already present, leave it alone; if missing, insert under the H1).

Putting the README edits in the same generator means the sync check
also catches "you added a spice but forgot to update the root table."

## Migration

One PR. The change set:

1. Add `tools/gen-spice-workflows.py`.
2. Run it once; commit the generated `spice-*.yml` files.
3. Add `.github/workflows/spice-ci-sync.yml`.
4. Move `manifest-parse` job into `.github/workflows/manifest-parse.yml`.
5. Delete `.github/workflows/ci.yml`.
6. Regenerate root README table + per-spice README badges.

PR description must include a one-line note that the aggregate
`ci.yml` badge URL is going away (any external links break -- the
audit below confirms there are none outside the README we already
updated). Land on `main` during a quiet hour.

---

## Validation

- Pre-merge: the sync-check workflow passes (no drift) and at least
  three per-spice workflows succeed on the PR itself (`tourist`,
  `frame`, `httpd` cover flat tests, nested tests, and `:cmake-deps`
  fetch).
- Post-merge: every per-spice badge URL resolves to a non-404 SVG
  within five minutes of the next push. Spot-check the README badges
  render correctly on github.com (PRs render Markdown differently
  from gh-pages, so check the live URL).
- Regression: open a PR that breaks exactly one spice (e.g., insert
  a syntax error in `spices/frame/src/...`). Confirm only the `frame`
  workflow fails on the PR; `tourist` etc. are not even queued.

---

## Risks

- **Workflow-file proliferation in the PR diff.** 34 generated files
  is a lot of green in a PR. Mitigation: the generator + sync check
  mean reviewers only need to read the template (in
  `gen-spice-workflows.py`) and trust the diff is mechanical. Include
  a one-paragraph reviewer note in the PR.
- **Drift between template and on-disk files.** The sync-check workflow
  catches this on PR. Failure mode is loud, not silent.
- **`paths:` filter false negatives.** If a spice depends on another
  spice's source (transitive change), the `paths:` filter for the
  dependent won't fire. Counter: today's matrix re-runs *everything*
  on every change so transitive deps are covered by brute force; this
  plan trades that for speed and per-spice signal. Two ways to handle:
  - **Conservative**: drop `paths:` from a spice that has cross-spice
    deps declared in its `build.tur`. The generator reads `:spices`
    entries and only adds `paths:` if there are no cross-spice deps.
  - **Liberal**: keep `paths:` and accept that a cross-spice break may
    not surface until that dependent is itself touched. The
    `manifest-parse` workflow catches gross breakage repo-wide.
  Recommend the conservative variant.
- **Aggregate "is the whole repo green?" signal disappears.** No single
  badge says "all 34 spices currently pass." Decision-record below.
- **GitHub Actions concurrency / queueing.** 34 workflows triggered
  by a single workspace-wide change (e.g., generator edit) all queue
  at once. GitHub's per-repo concurrency limits make this fine in
  practice, but on a free runner plan it can stretch wall-clock.
  Mitigation: add `concurrency: group: spice-${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true` to each per-spice
  workflow so an in-flight run is canceled when a new commit lands.

## Decision Records

### DR-1: No aggregate badge after the split

We considered keeping a thin `ci-aggregate.yml` workflow that depends
on every per-spice workflow's last status, just to preserve a single
"everything green" badge. Rejected: GitHub doesn't have a clean
"depend on the last run of another workflow" primitive (`workflow_run`
is per-event, not per-status), and emulating it with the API is the
exact bespoke-infra path this plan is trying to avoid. The honest
read on "is the whole repo green" is the Actions tab, not a badge.

### DR-2: Keep one shared template, not per-spice hand-written files

Per-spice hand-written workflows would let each spice customize CI
(extra system deps, longer timeouts, etc.). Rejected for v1: the
homogeneity is the point. If a spice needs a custom step later,
extend the generator to read an optional `requires.ci-extras.yml`
in the spice root.

### DR-3: Generator + sync-check vs. composite action

A composite action (`uses: ./.github/actions/test-spice`) would let
us keep one source-of-truth file (the composite) and have each
per-spice workflow be a 6-line stub. Considered. Rejected because:

- The 6-line stubs still need to exist as files for the badge URLs
  to work, so the file-count argument doesn't actually shrink.
- Composite actions can't define matrices, so `os: [ubuntu, macos]`
  would have to live in each stub anyway.
- The generator approach keeps the **whole workflow body** in the
  template, which is easier to read and audit than splitting half
  into a composite and half into stubs.

We may revisit this if the per-spice workflows grow non-trivial
divergence; the generator can switch to emitting composite-using
stubs later without breaking the badge URLs.

## Open Questions

- Should the generator also emit a `docs/spices-ci-status.md` page in
  this repo (turmeric) that lists every spice + badge, similar to a
  status dashboard? Cheap to add, but duplicates information already
  visible on github.com/rjungemann/turmeric-spices and adds a
  cross-repo sync surface. Defer to follow-up if requested.
- Should the per-spice workflow include a step to publish a JSON
  manifest (spice name + last result + timestamp) to a gh-pages
  branch, enabling a shields.io custom-endpoint badge for *aggregate*
  view? Rejected in DR-1 above, but recording the question in case a
  future operator wants it.
- Concurrency tuning: should the `concurrency.group` key include the
  spice name (so two spices can run on the same ref) or only the ref
  (so any new commit cancels all in-flight per-spice runs on the same
  ref)? Default to per-spice-per-ref (the looser version) so a quick
  follow-up commit cancels just the spices it touched.

## Validation Checklist (for the implementing PR)

- [ ] `tools/gen-spice-workflows.py` exists and runs without args from a
  clean checkout.
- [ ] `tools/gen-spice-workflows.py --check` passes on a freshly
  generated tree.
- [ ] `tools/gen-spice-workflows.py --check` fails when a generated
  file is hand-edited or when a spice is added without regenerating.
- [ ] Every `spices/<name>/` has a corresponding
  `.github/workflows/spice-<name>.yml`.
- [ ] No orphan `spice-*.yml` for a non-existent spice.
- [ ] `.github/workflows/ci.yml` is deleted.
- [ ] `.github/workflows/manifest-parse.yml` runs on every PR.
- [ ] `.github/workflows/spice-ci-sync.yml` runs on the PR that adds
  the system, and passes.
- [ ] Three representative spice workflows succeed on the
  implementing PR (`tourist`, `frame`, `httpd`).
- [ ] Root `README.md` table is regenerated.
- [ ] Per-spice `README.md` badges are inserted (or already present
  and left alone).
- [ ] An intentionally-broken-spice test PR (one syntax error in one
  spice) shows exactly one failing workflow.
