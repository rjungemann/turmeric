# `tur run test` never reaches ctest -- the doctest dependency fails first

**Severity: medium** (the project's own top-level test recipe does not run the
test suite). Found 2026-08-20 while restoring `-j` to the same recipe
(`justfile-test-recipe-lost-ctest-j`).

## Repro

```sh
tur run test          # or: just test
echo $?               # 1, in ~24s -- far too fast for the suite
```

The recipe is `test: build doctest` followed by the ctest line. `doctest` runs
`tools/run-doctests.sh`, which exits 1 when any case fails
(tools/run-doctests.sh:155-160). That non-zero exit stops the chain, so **the
ctest line never executes**. The 24s wall clock is the giveaway: a real run is
minutes.

This is orthogonal to the `-j` regression next door -- restoring `-j` (done)
makes the ctest line correct, but the line is still unreachable.

## Current failures -- 50 cases across 4 modules

| Module | Cases | Shape |
|---|---|---|
| `rational` | 34 | cascade from one lint |
| `term` | 10 | `got "-1", expected "0"` |
| `panic` | 5 | cascade from one compiler warning |
| `seq-core` | 1 | `got "false", expected "true"` |

Two distinct causes:

**1. Diagnostic output desynchronises the expected/actual pairing.** The
`rational` and `panic` blocks are not 34 and 5 independent failures. The
compile emits a diagnostic on stderr -- for `rational` the
`unsafe block has 29 expressions (threshold: 20)` lint, for `panic` a
`-Wreturn-type` warning -- those lines land in the captured output, and every
subsequent case is then compared against the wrong line. The tell is failures
like ``got "1 | ; AUTO-GENERATED by tools/doctest.py -- do not edit.",
expected "2"``: the runner is reading the diagnostic's source echo as program
output. Silence or filter the diagnostics and both blocks likely collapse to
one real failure each, or zero.

**2. Genuinely wrong expectations.** `term/set-mode`, `term/set-raw`,
`term/set-cooked` etc. return `-1` where the docstring claims `0` -- these are
tty ioctls with no tty attached under the runner. `seq-core:empty-seq` returns
`false` for `true`. These are real docstring/environment mismatches.

Note `random:rand-bool` also fails intermittently (`got "0", expected "1"`) --
the docstring pins a coin flip, so the total oscillates between 50 and 51.

## Fix direction

1. Make the runner robust to diagnostics on the compile step -- capture
   stdout only, or filter `warning:`/`note:` lines before pairing. That alone
   should clear ~39 of the 50.
2. Fix or environment-gate the `term/*` tty cases (skip when
   `!isatty(STDIN_FILENO)`), `seq-core:empty-seq`, and the `random:rand-bool`
   coin flip.
3. Decide whether `test` should hard-depend on `doctest`. Given that doctests
   check *documentation examples*, gating the entire ctest suite behind them
   is a strong coupling; a separate `just doctest` plus a non-blocking report
   in `test` may fit better. Whichever way, `tur run test` must reach ctest.

## Scope note

Verified as pre-existing rather than branch-introduced by scope: the failing
modules are `rational`, `term`, `panic`, `seq-core`, and
`git diff --name-only origin/main...HEAD` touches none of them (the only
stdlib change on the branch is `stdlib/cstr.tur`, whose 4 doctest cases pass).
