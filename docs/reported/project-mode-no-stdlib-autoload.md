# Project-mode (`tur build .`) does not auto-load stdlib

## Summary

`tur build <file.tur>` (single-file) auto-loads ~30 stdlib files
(`macros.tur`, `option.tur`, `result.tur`, `list.tur`, etc.), making types
like `Cons`, `Option`, helpers like `tnil?` / `tcons`, and the typeclass
class stubs (`Functor`, `Hash`, ...) available without any explicit import.

`tur build .` (project / multi-file) does **not**. Each module's compilation
unit runs through `compile_to_h` (`src/main.c:986`), which only injects the
project prelude — no stdlib forms are prepended. The result: a spice can
write code that single-file-compiles fine but fails the project build with
"kind mismatch" + "unknown function" cascades the moment it touches a
stdlib type by an unqualified name.

## Repro

Smallest faithful repro (no JSON involvement):

```turmeric
;; src/myspice/foo.tur
(defmodule myspice/foo
  (export bar)

(defn bar [A] [cell : (Cons A)] : int
  (if (tnil? (:: cell :int)) 0 1))
)
```

```turmeric
;; build.tur
(defpackage my :name "my" :version "0.1.0"
  :exports #{ "myspice/foo" ["bar"] })
```

```
$ tur build .
./src/myspice/foo.tur:4:23: error [TUR-E0012]: kind mismatch:
  cannot apply a type of kind '*' as a type constructor; expected '* -> *'
./src/myspice/foo.tur:5:8: error: unknown function or operator 'tnil?'
```

Same file via `tur build src/myspice/foo.tur` (single-file) compiles
without diagnostics, because `compile_to_c` (`src/main.c:603`) loops over
`stdlib_files[]` and prepends each file's forms before elaboration.

## Real-world impact

This blocks `../turmeric-spices/spices/json` from building in project mode
(`json/encode.tur` uses `(Cons A)` and `tnil?` in a `defmodule`). Json is
a transitive dep of `httpd`, which is a dep of `tourist`. So nothing
downstream of json can produce its build artifacts (`httpd__types.h` et
al.), and every tourist app build fails on missing headers.

## Root cause

`compile_to_h` in `src/main.c:986` (project-mode path) elaborates its file
with only the project prelude (`load_project_prelude`), unlike
`compile_to_c` which constructs a `stdlib_files[]` list and reads every
entry into the same arena, prepending forms before
`elaborate_program`. The omitted block in `compile_to_c` is roughly
lines 670-845 of `src/main.c`.

## Fix sketch

Two paths, neither trivial:

1. **Auto-load stdlib in `compile_to_h` too.** Mechanically straightforward
   (lift the `stdlib_files[]` literal to file scope, extract the read/parse
   loop into a `prepend_stdlib_forms(arena, st, ...)` helper, call from
   both compile_to_c and compile_to_h). The risk: stdlib forms registered
   for emission via the project-mode path would duplicate-emit across every
   module's `.c` file, causing duplicate-symbol link errors. The right
   shape is to load stdlib in an "imported module" mode that registers
   bindings for elab visibility but skips `elab_register_file_def` —
   mirroring the gate at `src/compiler/elab_core.c:976`.

2. **Spices import stdlib explicitly.** Each spice that uses
   `Cons`/`tnil?`/`Option`/etc. would add an explicit `(load
   "stdlib/list.tur")` or similar. Less invasive on the compiler, but
   requires touching every affected spice and is at odds with the
   single-file UX (which auto-loads).

The first option preserves the contract that "spice code works the same
way as standalone .tur files" — almost certainly the right long-term fix,
once the duplicate-emission gate is wired correctly.

## Workaround for now

Single-file builds (`tur build path/to/file.tur`) still work. The tourist
case can be unblocked by manually running each transitive dep's build to
generate its headers, or — pragmatically — by editing
`spices/json/src/json/encode.tur` (and similar) to inline `cons`-walking
without the typed `(Cons A)` parameter type, which sidesteps the stdlib
visibility requirement entirely.

## Adjacent

Tourist's downstream `httpd__types.h not found` errors are a SECOND
architectural gap: `tur build .` doesn't currently chain into transitive
dep builds either. Even with stdlib visibility fixed, tourist would need
httpd's `.h` files generated by a prior `tur build ../httpd` invocation
(or by a build orchestrator at the workspace level).
