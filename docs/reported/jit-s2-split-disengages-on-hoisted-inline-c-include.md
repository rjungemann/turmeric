# S2 split silently disengages for any program with a hoisted inline-C include

**Severity: low-medium (performance, not correctness).** Affected programs
compile and run correctly; they just re-parse the full fixed runtime preamble
on every `tur jit` / `tur build`, which is exactly the per-program cost S2 was
built to remove. It fails closed, which is why it has gone unnoticed.

Found 2026-07-30 while measuring the macOS cc-fallback baseline for
docs/archive/jit-macos-apple-sdk-headers-force-cc-fallback.md.

## Summary

`jit_try_split_preamble` (`src/main.c:3329-3355`) swaps the emitted fixed
runtime preamble for the committed `tur_rt_split_decls` blob, guarded by an
xxHash64 compare (`src/main.c:3340-3341`) against a probe preamble produced by
`emit_rt_split_source` (`src/compiler/emit_module.c:10850-10865`).

Mechanism-1 hoisted includes -- the `#include` lines that elaboration lifts out
of the *leading* lines of an inline-C body (`tur_hoist_top_includes_scan`,
`src/compiler/emit_core.c:2966-3044`) -- are replayed at
`src/compiler/emit_module.c:7363-7364`, which sits **inside** the byte span the
split replaces.

`emit_rt_split_source` forces `g_needs_hamt` / `g_needs_regex_h` /
`g_needs_winsock` true so the probe matches, but it does **not** reset
`g_hoisted_includes`. So any program that hoisted an include emits a preamble
the probe cannot reproduce, the hash compare fails, and the split silently
disengages.

Net effect: **a program with a hoisted inline-C include never gets the S2 fast
path.**

## Minimal repro

Any `.tur` whose inline-C body *begins* with a bare `#include` line (the
scanner stops at the first line that is not blank / `//` comment / `#include` /
object-like `#define`, so a leading `/* ... */` block comment or `#if` prevents
the hoist and the split still engages):

```turmeric
(defn probe [] : int
  ```c
  #include <mach-o/dyld.h>
  return 0;
  ```)

(defn main [] : int (probe))
```

In-tree, `stdlib/image.tur:49-51` does exactly this (`#include <stdint.h>`,
`<windows.h>`, `<mach-o/dyld.h>`, deliberately bare-leading so the hoister
lifts them out of function scope), so the three `image-*` fixtures are live
instances. The whole `httpd-*` family is another, via `stdlib/httpd.tur`.

### Measuring it: a deliberate syntax error reveals the preamble length

c2mir reports diagnostics in TU line numbers, so a deliberate error deep in an
inline-C body reports a *higher* line when the full preamble is in front of it
and a *lower* one when the split's shorter decls blob is. Compile the same
program with and without `TUR_JIT_NO_SPLIT=1` and compare.

Program A -- no hoisted include (the leading line is not a `#include`, so
nothing is lifted):

```turmeric
(defn boom [] : int
  ```c
  int *p = 0;
  static const int q[3] = {1,2,3};
  return q[0] + syntax error here;
  ```)
(defn main [] : int (boom))
```

Program B -- identical but with one bare leading `#include`, which the scanner
lifts:

```turmeric
(defn boom [] : int
  ```c
  #include <stdint.h>
  return 0 + syntax error here;
  ```)
(defn main [] : int (boom))
```

Measured on arm64 macOS, 2026-07-30:

| program | default | `TUR_JIT_NO_SPLIT=1` |
|---|---|---|
| A (no hoisted include) | **5474** | 7097 |
| B (one hoisted include) | **7098** | 7098 |

Program A shows the split working: ~1,623 fewer lines in front of the program
body. Program B is identical with and without the split, and identical to A's
un-split number -- the split did not engage.

Note also that A emits `TUR-W0071: split-runtime path failed to compile;
retrying with the full preamble` (its deliberate error trips the retry), while
B emits no `TUR-W0071` at all. That distinction matters: B is not
engaging-then-failing, it is **never engaging**. Do not use the absence of
W0071 as evidence the split succeeded.

## Why it matters beyond the fixtures

The code comment at `src/compiler/emit_module.c:7357-7360` names the real
consumers of the hoist mechanism: `sqlite3.h`, `rtmidi_c.h`, `lo/lo.h`. Any
spice binding a C library through inline-C is therefore paying the full
preamble parse on every build, which on Apple Silicon is the dominant cost
(c2mir is 73% of engine time, findings 20.4).

## Fix directions

1. **Move the hoisted-include replay above the split marker.** The replay only
   needs to precede the first inline-C function; it does not need to be inside
   the fixed-preamble span. Emitting it ahead of
   `/* generated by tur (phase 2) */` keeps the split's probe reproducible and
   costs nothing. Cheapest fix.
2. **Or fold `g_hoisted_includes` into the probe.** Have
   `emit_rt_split_source` replay the same list so the hash matches. Keeps the
   current emission point but couples the probe to elaboration state, which is
   the coupling that produced this bug.
3. **Diagnose the disengage.** Whichever route is taken, the silent failure is
   the real defect -- a `TUR_JIT_VERBOSE`-gated note when the hash compare
   rejects the split would have surfaced this immediately.

Option 1 is the fix; option 3 is worth doing regardless.

## Verification

`bash tests/run-jit.sh` does not measure this (the split is invisible to
pass/fail). Measure directly: time `tur jit` on an image-* or httpd-* fixture
before and after, or instrument the hash-compare branch to log when it rejects.
