# CPS backend: fn-value (fat-closure) parameters diverge in name and C type from the direct emitter

**Severity:** medium (blocks the N6.4 "indirect calls" sub-slice; no miscompile
today because an indirect call forces whole-function fallback).

## Summary

An indirect call (`(fnv arg)` where `fnv` is a function *value*, `fn_binding ==
NULL`) currently lowers to `CT_UNSUPPORTED "indirect call"`, so the enclosing
colored function falls back to the direct emitter. Delegating the indirect call
to the direct emitter via `CT_LETRAW` (the same path uncolored direct calls
already use) is semantically sound -- the fn value is the callee's direct entry,
which never joins the caller's delimited-control chain -- BUT it miscompiles,
because the CPS backend and the direct emitter disagree on how a fn-value
*parameter* is spelled in C.

## Minimal repro (with indirect-call delegation enabled; reverted)

```turmeric
(defeffect E [] :int)
(defn g [] : int (perform (E)))
(defn dbl [n : int] : int (* n 2))
(defn f [fnv : (fn [int] int)] : int
  (let [base (fnv 10)]                       ; indirect call
    (+ base (handle (g) (E [] k) (resume k 50)))))
(defn main [] : int (println (f dbl)) 0)
```

Emitted `f__cps` (with delegation):

```c
static int64_t f__cps(void * fnv_1268, DK *k) {                 // (1) param typed void*
    __auto_type __ps = (((int64_t(*)(void*,int64_t))fnv.fn)(fnv.env, INT64_C(10)));
                                              // ^^^ (2) names it `fnv`, treats as tur_poly_fn_t
    ...
}
```

`cc` fails: `'fnv' undeclared`. Two divergences:

1. **C type:** the CPS backend types the fn-value param as `void *`; the direct
   emitter's signature is `static int64_t f(tur_poly_fn_t)` -- a fat closure
   struct (`.fn` / `.env`).
2. **C name:** the delegated body (direct emitter) refers to the value as the
   bare source name `fnv`; the CPS backend names the param `fnv_1268`
   (`name_for_binding`). For ordinary scalar/aggregate params the two agree
   (e.g. `p_1268`), so delegated `get-field` / `make-struct` on a param work --
   the divergence is specific to fn-value (fat-closure) parameters.

## Root cause

`src/compiler/emit_cps_ir.c` param-signature emission does not special-case a
fat-closure (`tur_poly_fn_t`) parameter the way the direct emitter
(`emit_fns.c` / `emit_expr.c`) does -- it falls through to `void *` and to the
id-suffixed name. A delegated body generated by the direct emitter then
references a name/type the CPS signature never introduced.

## Fix directions

Teach the CPS backend's parameter typing + naming to match the direct emitter
for fn-value parameters: emit `tur_poly_fn_t <bare-source-name>` (or whatever
`emit_fns.c` uses) so a delegated `EX_CALL` with `fn_binding == NULL` resolves
`fnv.fn` / `fnv.env` against a real local. Once the param spelling agrees, the
indirect-call delegation itself is trivial (route `!fn_binding` through
`build_letraw` when `call_args_atomic`, exactly as uncolored direct calls are
routed) and sound. The scanners (`has_capture_rec` / `collect_caps_rec`) also
need the `EX_CALL` arm to enumerate `fn_expr` when `fn_binding == NULL`, so an
indirect call in a lifted continuation captures its fn value.
