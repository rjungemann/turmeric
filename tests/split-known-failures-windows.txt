# Fixtures known to fail under TUR_RUNTIME=split on WINDOWS (MSYS2/UCRT64,
# MinGW gcc, Debug). The Linux job has its own list in
# tests/split-known-failures-linux.txt -- the two are genuinely different, and
# that difference is the reason this file exists.
#
# NAMES, not a count. See the linux file's header for why.
#
# How the Windows job uses this, and why it differs from the Linux one: the
# Windows suite is SHARDED three ways (a single runner took 28-52 minutes and
# once died outright), so no single shard sees the whole corpus. Each shard
# therefore asserts its failures are a SUBSET of this list -- which catches
# every new failure, immediately, in whichever shard it lands. The opposite
# direction, a listed fixture that has started passing, is checked once by
# running exactly these names unsharded; that run is however many names are
# below and costs seconds.
#
# If you fix one, delete its line in the same commit: the second check turns
# red on a fixture that passes while still listed here.

# --- FIXED 2026-09-07: hamt-lowering-basic, the "genuinely lossy" one -------
#
# NO LONGER LISTED, on either platform. It was described here as the one place
# the split is irreducibly lossy. It was not -- the loss was in throwing away
# information the input already carried.
#
# The emitted preamble is not fixed across programs: the emitter writes EITHER
# `#include "hamt.h"` (a program the compiler lowers straight onto the hamt API)
# OR loose `extern void *tur_hamt_new();` declarations from stdlib's extern-c.
# Never both, because gcc rejects the pair outright -- confirmed directly:
#
#   error: conflicting types for 'tur_hamt_new'; have 'void *()'
#   note: previous declaration ... with type 'Hamt *(void)'
#
# The committed decls region is generated from ONE canonical emission, so
# whichever shape that program used was frozen for everybody. Carrying the
# include unconditionally broke every loose-extern program; guarding it out
# broke every program needing the header. Both were true, which is why this
# looked like a trade-off with no good side.
#
# The fix is not to choose: jit_try_split_preamble now re-emits the quoted
# includes the REPLACED REGION actually contained (src/main.c), so each program
# gets exactly what it emitted -- the monolithic behaviour, restored. Verified
# on 133 hamt/map/dict/set fixtures under split: 0 failed.

# --- FIXED 2026-09-07: was a stack overflow, not a GC bug -------------------
#
# NO LONGER LISTED. The fix is in tools/gen-runtime-split.py (INLINE_INTO_DECLS);
# gc-registry-growth now passes under --runtime=split, and the prologue is back
# to the monolithic build's `sub $0x48,%rsp`. Kept in full because the
# investigation is the valuable part and the seam it found is still live.
#
# It is NOT a defect in the rc/GC machinery, and the "exit 127, no output" this
# file used to describe was a red herring the whole time. In bash 127 is a
# translation; the real status is 0xC00000FD == STATUS_STACK_OVERFLOW
# (PowerShell reports LASTEXITCODE=-1073741571). Nobody looked past the 127.
#
# Mechanism. The monolithic preamble emits `tur_frame` AND its two accessors
# into the same TU as the program, as `static inline`
# (src/compiler/emit_module.c:10092-10103). The split replaces that region with
# the committed decls header, where the same two are bare extern prototypes
# (src/runtime/generated/tur_rt_split_decls.h:615-616) with out-of-line bodies
# in libturt_preamble.a (src/runtime/generated/tur_rt_split.c:1042,1045).
#
# De-inlining them is deliberate -- tools/gen-runtime-split.py:71-77 documents
# it, naming tur_frame_init as the very function that forced it -- and it is
# right for linking and wrong for codegen. Inlined, GCC sees a frame holding
# one known thunk and eliminates the 536-byte struct. Split, `&__frame_N`
# escapes to an opaque callee, so all 536 bytes must be real:
#
#   build_hychain prologue, same compiler, byte-identical program C:
#     default   sub $0x48,%rsp
#     split     sub $0x268,%rsp
#
# 20000 frames x 640 bytes = 12.2 MiB against a 2 MiB Windows stack reserve
# (identical SizeOfStackReserve in both PE headers -- not a link-flag
# difference). Predicted overflow depth 2097152/640 = 3276; measured, split
# prints at 3200 and dies at 3300. Relinking the same split build with
# -Wl,--stack,33554432 makes it print 20000 and exit 0.
#
# CORRECTION, and the reason this sat misdiagnosed. An earlier revision of this
# file recorded "NOT recursion depth -- a hand-written 20000-deep recursion runs
# fine under split". That experiment was mine and it was wrong: the probe had no
# `defer` in its body, so it never allocated a tur_frame at all. It eliminated
# depth ALONE; the actual variable is depth x defer-bearing scope. A 20000-deep
# recursion whose body is `let [r (rc/of n)]` fails identically under split and
# passes under default. A negative result is only as good as the thing it varied.
#
# The tur_sjlj_x64_win.S hypothesis this file used to carry is dead: the minimal
# repro reaches the fault with no setjmp, no panic and no async.
#
# THE FIX, as actually applied, which differs from the direction first written
# here in two ways worth recording:
#
#  - It is THREE helpers, not two. Inlining tur_frame_init and
#    tur_frame_push_defer alone changed nothing measurable -- the prologue
#    stayed at 0x268 -- because the emitter also writes
#    `tur_frame_fire_lifo(&__frame_N)` at scope exit, and one surviving opaque
#    callee is enough to make the address escape. It is plain `static` in the
#    preamble rather than `static inline` (emit_module.c:10110), so it does not
#    turn up when you grep for the inline ones.
#  - The archive copies are KEPT, not omitted. The first attempt omitted them;
#    that works for the first two (nothing in the archive calls them) but not
#    for fire_lifo, which tur_frame_fire_chain calls from inside the archive.
#    `static inline` has internal linkage, so keeping both is free of conflict
#    and removes the need to reason about which archive function calls which.
#
# Result: prologue back to `sub $0x48,%rsp`, identical to the monolithic build,
# and the fixture prints 20000 and exits 0 under --runtime=split.
#
# Still worth doing separately: shrink tur_frame itself, three fixed 32-entry
# arrays sized for a common case of 1-2 defers.
#
# TWO FURTHER FINDINGS, both worth their own attention:
#
#  1. The DEFAULT runtime is also near the cliff on Windows. Measured: the
#     fixture passes at depth 21000 and overflows at 21800, matching
#     2097152/96 = 21845. At its committed depth of 20000 it uses ~1.83 MiB of
#     a 2 MiB stack -- about 9% headroom. Any codegen change that adds a few
#     bytes to that frame breaks this fixture in the DEFAULT runtime too, and it
#     will present as the same content-free "exit 127". Nothing in src/ or
#     tests/run.sh ever passes -Wl,--stack, so every tur-built Windows binary
#     gets 2 MiB where Linux gets 8 MiB.
#
#  2. Why this passes under split on LINUX is not established, and the
#     arithmetic says it should not: at 20000 frames an 8 MiB stack allows 419
#     bytes, less than sizeof(tur_frame) = 536 on its own. Either the Linux
#     frame is smaller than can be accounted for, or the split DECLINED the swap
#     for this program there (it declines loudly on hash mismatch --
#     src/main.c:2681-2688 -- and hamt-lowering-basic's note confirms the
#     emitted preamble is not fixed across programs), in which case the Linux
#     green is vacuous for this fixture. One check on a Linux box settles it:
#     build with --runtime=split, `objdump -d` the build_hychain prologue and
#     read `ulimit -s`. A ~0x230 sub means the same latent cliff exists there;
#     a ~0x30 sub means the split declined.
